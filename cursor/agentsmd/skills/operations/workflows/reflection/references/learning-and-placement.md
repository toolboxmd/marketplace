# Learn without accumulating rules

## Diagnose why guidance failed

Read the current proposed owner before accepting a lesson. Distinguish:

| Failure | Useful correction |
| --- | --- |
| Guidance missing | Add the smallest rule or mechanism that changes the decision |
| Existing guidance not selected | Improve description or loading trigger |
| Guidance buried or ambiguous | Fix placement, ordering, conditions, or completion criteria |
| Clear guidance loaded but ignored | Investigate execution; duplicate prose is not a repair |
| A preventable mechanical error | Prefer a schema, check, metadata field, or bounded tool |

An enforceable constraint often belongs in structure. A validated constructor
can prevent invalid state; a dependency edge can prevent premature dispatch;
a link check can prevent a missing reference. Keep rationale, exceptions, and
authority text where the mechanism cannot express them. A rule's existence is
not proof that its enforcement is complete.

## Accept a lesson that changes a future decision

State the observed problem, generalizable mechanism, actual scope, proposed
change, owner, and evidence that would falsify the lesson. Distinguish a repeated
pattern from one explicit preference or an exceptional event. A single clear
user instruction can establish a preference without repetition. A lone accidental
success does not establish a universal best practice.

Prefer durable guidance, but retain useful version-specific host quirks with their
scope and recheck trigger. Do not turn today's tool limit into permanent policy.
Do not restrict learning to previously invoked skills when the evidence reveals
a missing capability; justify the new trigger and owner instead.

Reject speculative improvements, duplicated rules, and rules that merely rename
the failure. Record a rejected proposal's reason when it prevents costly
rediscovery. Publish follow-up Issues only when the task authorizes that mutation.
Do not automatically append a backlog after a read-only reflection.

## Put the result in its existing home

| Content | Owner |
| --- | --- |
| Personal working defaults | Adjacent private `PREFERENCES.md` under the canonical instructions |
| Agreed project language | Project glossary through [domain-modeling](../../domain-modeling/index.md) |
| Costly architectural decision | ADR under the existing eligibility rule |
| Reusable workflow | Its owning procedure, external Skill, or canonical operating reference |
| Current implementation/delivery state | Owning Issue and exact proof |
| Temporary observation | Task evidence with an explicit limit, not global policy |

Reflection does not alter confirmed Project Direction or expand authority. Read
and preserve the complete current owner before editing. Improve the selection
mechanism rather than pasting the same procedure into every caller.

Apply [artifact placement](../../../references/artifacts.md) if supporting evidence
must be retained. Correct the existing owner instead of appending a reflection
diary, memory database, or new backlog. No durable finding means no new file.

## Capture personal preferences privately

Apply only when personal-preference work is requested. Locate and read the real
private preferences first. Scope history to the relevant user, topic, and time
range, using changes since the last known review when reliable metadata exists.
Compare repeated patterns with explicit current intent. Resolve contradictions
by time and context; do not average incompatible instructions into a vague rule.

Propose non-default working choices in the user's own terms. Confirm inferred
meaning when it changes future behavior; an explicit current instruction already
supplies intent. Preserve non-contradicted sections. Link existing workflows
instead of copying a personal operating system around them.

Keep evidence and private contents out of public Issues, reports, commits, and
Skills. Do not create a public personal-mode wrapper, scrape unrelated histories,
or invent a new preference database. Private defaults cannot waive mandatory
context, authority boundaries, user-owned state, or confirmed direction.
